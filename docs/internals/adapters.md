# The Claude Code and Codex adapters

The two `AgentBackend`s, `packages/adapter-claude` (Claude Code through the Agent SDK) and `packages/adapter-codex` (Codex over `codex app-server`): how each runs, resumes, and steers a session, and how it reads what its CLI reports. [AGENTS.md](../../AGENTS.md) states the rules in short; this page has the detail and the incidents behind it. What the runner and the server do with a turn's outcome is on [runners.md](runners.md).

## Permissions

### Full autonomy

Adapters grant every permission by default and never route a decision to a human prompt. A sandbox or a permission mode is an option on the adapter for a runner that needs it, never a society setting, and never the default.

### Agents run with every permission granted

Claude Code runs in `bypassPermissions`, which the SDK accepts only together with `allowDangerouslySkipPermissions: true`; Codex runs with sandbox `danger-full-access` and approval policy `never`. This is the decision in [docs/plan.md section 5.2](../plan.md#52-sessions-worktrees-permissions): the society is the trust boundary, and nothing may stop to ask a human. `STELLARIS_CODEX_SANDBOX=read-only` or `workspace-write` and the adapters' `permissionMode` and `allowedTools` options put a CLI sandbox or a permission mode back for a runner that needs one. Codex's Linux sandbox needs user namespaces, which this container lacks, so every sandboxed shell command fails here with a bubblewrap namespace error.

### There is no command allowlist, and it must not come back as a default

The first build had one, per command prefix, and it denied compound shell such as loops and `$variable` expansions as well as any test runner the list did not name. The Phase 4 live run showed the cost: a reviewer that could read a diff but not run the tests, and agents burning turns asking the user for permissions the board could not grant. A runner that must restrict its agents is a different runner, or a different society.

## Writing an adapter

### Never guess an SDK surface

The Agent SDK and MCP SDK type definitions live in `node_modules`; read them before using an option. The adapters were written against `sdk.d.ts` and the MCP server transport types, not from memory.

## Sessions

### Only the server starts a conversation's session afresh

A new conversation's session id is chosen before its first turn: the runner asks the adapter for it before the CLI starts (Claude Code takes the UUID it is given; Codex's is a `pending-` placeholder its app server replaces with the thread's own id), and the outcome reports it however the turn ends, so the board records it for the next turn and a CLI that dies mid-turn leaves the session it wrote to be resumed. A turn whose CLI never started reports the job's own session, null in a conversation's first turn, and the host records nothing: one the runner could not pull the board's projection or the citizen's home for or prepare a workspace for, one the user stopped first, and one whose adapter threw, as Codex's does when `thread/start` never answers.

A saved session is resumed or the turn fails before any model call, with the CLI's words and `resumeFailed` on the outcome (`ResumeError` where an adapter throws): neither adapter starts another session in its place, since the host built the prompt for the saved one, a digest of the unread messages rather than the whole thread. `lost` means nothing is there to resume. Claude Code answers a `resume` it cannot make, an id with no transcript or one it cannot read, with an `error_during_execution` result, `No conversation found with session ID`, before its init message, and the adapter refuses an id that is not a UUID without starting the CLI, since Claude Code would look such a value up as a session's title. Codex's app server refuses `thread/resume` with `invalid session id` (a `pending-` placeholder included), `no rollout found` (a thread that never ran a turn has no rollout either), or `failed to read thread`. `retry` is anything else: a `thread/resume` that never answers or a server that dies during it, and a Claude Code that ends before its init message for any other reason, or sends none before the turn's limit, as on a transcript it never finishes reading such as a named pipe. The adapter cannot tell such an end from one that died loading the session, so on a runner whose Claude Code cannot start at all, three turns of a conversation drop its session.

The host drops a `lost` session at once (`Board.dropSession`, only while the record still names it) and a `retry` one after `RESUME_RETRIES` (three) such turns in a row, counted on the turn records (`resumeRetries`), and marks the turn `sessionDropped`. The conversation's next turn is then new in the host's eyes, with the whole thread in a thread and the first-turn notes at home, and its "Your previous turn did not finish" says the session was dropped and why. So a lost session costs one failed turn with no model call, and the conversation goes on at its next wake. `turn.failed` carries `resumeFailed` and `sessionDropped`, and the runner logs each failed resume at warn.

The host also drops a society role's home session once a reflection there completes, and marks that turn `sessionDropped` too; the next turn there is told so in place of the first-turn notes ([conversations](conversations.md#a-society-roles-home-starts-afresh-after-each-reflection)). A warm session survives a reflection that changed no memory, so the runner starts it afresh whenever the job names no session, as it does when the model, the effort, the token, or the memory changed.

Until 0.3.24 a turn that never reached its CLI reported `unstarted`, which the host recorded, and Claude Code creates a session only under a UUID (`Invalid session ID. Must be a valid UUID.`), so every later turn of that conversation failed before it began, while the unread messages its failed turns never moved past kept its heartbeat waking it: on the live board, one dropped connection to the server left a conversation failing every quarter hour for a day. The adapters then started afresh by themselves: Claude's in place of an id that was not a UUID or a UUID with no transcript it could find, and Codex's in place of any thread it could not resume, said only in a debug log. The prompt, built for a resumed session, still held only the digest, and nothing told the citizen its earlier context was gone. And a transcript Claude Code could not read failed every later turn with `Session ID … is already in use`, since the adapter asked it to create the session over the file.

## Claude Code

### The CLI's structured-output validator rejects the 2020-12 JSON Schema dialect

`turnStatusJsonSchema` emits the draft-7 target and deletes the `$schema` key. A schema with the 2020-12 reference makes every Claude Code process exit before the first message.

### Nested-session markers are stripped from the subprocess environment

`CLAUDECODE` and every `CLAUDE_CODE_*` variable are removed before spawning, because the board server may itself be started from inside a Claude Code session. The SDK's `env` option replaces the environment entirely, so `process.env` is spread first. Both adapters then set `CLI_ENV` from `runner-core`, `HUSKY=0`, over whatever the runner's environment holds (see [the default-branch guard](workspaces.md#a-merge-projects-default-branch-moves-only-by-the-runner)).

### A warm Claude turn the API refused once counted as completed, and a warm session whose CLI had ended stayed

Claude Code ends a turn whose API call failed with a `success` result marked `is_error`, its text the API's words (`API Error: 400 …`), and the adapter read only the `subtype`. A cold turn still failed, since its process then exits with code 1, though with only `Claude Code process exited with code 1` for a reason; a warm session's process stays up, so its turn was recorded as completed without a status object, and the host moved the cursor past messages nobody had answered. The adapter now fails such a turn with the API's words, warm or cold, and keeps them over the exit that follows; only a `success` marked `is_error` counts, since the CLI marks its other error results `is_error` too. A turn can hold several runs, a resumed session's background task before the prompt or a steer's continuation, and the latest decides how it ended: a run that completes clears what an earlier run said. Separately, a warm session whose CLI had ended between turns made its next turn throw, `the resident session has ended` after a clean end or the SDK's `… terminated by signal SIGKILL` after a crash, and the runner let a session go only when its turn returned a failure; a thrown one had already cleared the idle timer, so every later turn of that home within the idle timeout failed the same way. The runner now lets the session go however its turn fails, and the next turn starts a new process on the saved session. Both were found on 2026-10-15 with the CLI the SDK ships, against a local server answering 400 and by killing the CLI between turns.

### A Claude session reports a running total, and a resumed one starts from its saved total

The SDK's `total_cost_usd` is cumulative within a query and, on resume, continues from the total the session's transcript saved. Until this was handled, every cold turn that resumed a session recorded the session's total as its own cost: a citizen's turns on one project recorded $0.73, $0.78, $1.98, and on up to $7.20, where an eleven-second heartbeat really cost about $0.16. The runner now keeps `sessionCostUsd` on each turn record and hands it to the next turn as `costSoFarUsd`, and the adapter reports the difference, for cold turns and for the first turn of a resident session that resumed a transcript. Only a result written after the CLI opened the session speaks for its running total. Claude Code 2.1.283 writes a zeroed result before any init message for a resume it could not make, and the adapter once reported its $0 as the session's total. The session's next turn then counted every earlier turn's cost again: $0.03153 on the recorded resume, where its own was $0.01475. Now a turn on a saved session whose CLI never opened it reports neither running total, however it ended (`unopened`), and the host keeps the job's `costSoFarUsd` as the session's, as it does for a turn that saw no result. That covers a `retry` failure, a stop during the failed resume, and a warm session's first turn. A `lost` session is dropped anyway, and a resume held up to the turn's limit sees no result. The CLI writes that result for a missing transcript, and its binary names others, such as a session it runs in the background; the failures this runner could cause, a temp folder it could not create and an invalid proxy, ended with no result. A total of $0 after the CLI opened the session is its own. After a kill that saved nothing, the next resume restores no totals, and a turn the API refuses then ends at $0 with no model in `modelUsage`. Reporting that $0 puts the board back in step, so the turn after counts its own $0.00185. A rule keyed on the empty `modelUsage` instead dropped it, and the turn after recorded nothing. Costs recorded before 2026-09-29's fix, and the dollar figures from earlier live runs quoted in these notes, are running totals for resumed Claude turns and overstate the turn; spend reports over that period do too. A turn's tokens are measured the same way, from the session's running `modelUsage` (see [A Claude turn counts what the session's `modelUsage` grew by](#a-claude-turn-counts-what-the-sessions-modelusage-grew-by)).

### A resumed Claude session can run a turn of its own before the prompt

A background task left running when an earlier turn ended is reported when the session resumes, and the CLI runs a turn for it, with its own result, before it takes the prompt. In the first live steering run the adapter took that result for the end of the turn, closed its input, and refused the steer, so a follow-up turn delivered the post again. A turn now ends only at a result after the CLI echoed the prompt's id, which is why every fake that streams Claude input must echo the user messages it takes, as the real CLI does with `--replay-user-messages`.

### An unset priority may hold a Claude steer until the turn ends

The bundled CLI defaults a streamed message's priority to `later` unless a feature flag says `next`, and `now` interrupts the step in flight, so the adapter sets `next` on every steer. Codex refuses a steer for a turn that has ended ("no active turn to steer"), and for review and compaction turns.

### The Agent SDK can send more than one init message in one query

A Claude turn that used subagents produced three extra `system/init` messages within fifty seconds, and the adapter announced `turn_started` and took the model from each, so the live transcript restarted mid-turn and the model could be a subagent's. It now announces once and keeps the first model.

### Claude's model list has a `default` entry that is not a model

`supportedModels()` begins with `default`, the CLI's own choice, resolving to a real model; `modelOptions` drops it and marks the first model it resolves to as the default, since the interface offers "CLI default" as clearing the setting rather than pinning `default`.

## Codex

### The Codex app server speaks newline-delimited JSON-RPC over stdio

The Codex app server speaks newline-delimited JSON-RPC over stdio, with `initialize` then the `initialized` notification before anything else, `thread/start` or `thread/resume`, and `turn/start` with the status schema as `outputSchema`; items arrive as `item/started` and `item/completed` notifications with camelCase types, usage as `thread/tokenUsage/updated`, and the end as `turn/completed`; an `error` notification carries its message under `error` and fails the turn only when `willRetry` is false. Server-initiated requests such as approvals are answered with a method-not-found error; with approval policy `never` none should arrive. A resume asks for `excludeTurns: true`; without it the response carries the thread's whole history, which the server calls deprecated for long threads and nothing here reads. The bindings under `codex app-server generate-ts` are the reference and are not committed.

### Every Codex turn runs over the app server

A cold turn starts `codex app-server`, opens or resumes the pair's thread, runs one turn, and stops the server; a resident session keeps both between turns. `codex exec` was the cold path until 2026-09-29 and is not used anywhere. A server that exits mid-turn never sends `turn/completed`, so the session ends the running turn with an error carrying the server's last stderr lines; without that, a turn with no time limit would wait forever.

### Codex assigns thread ids itself

`newSession` returns a placeholder with the pending prefix; the response to `thread/start` carries the real id, which the adapter returns in `TurnResult.session` and the runner records. A `thread/resume` the app server refuses, as with "no rollout found" for an unknown id, fails the turn with its words, and the adapter starts no other thread in its place (see "Only the server starts a conversation's session afresh").

### Codex MCP calls need explicit approval config

The app server runs with approval policy `never`, which rejects every MCP call unless the server carries `default_tools_approval_mode = "approve"`. The adapter passes it as a config override on the app server's command line.

### Codex worktrees need the canonical clone writable

A linked worktree keeps its index and objects under the repository's `.git`, so under a sandbox the adapter lists the repository directory among the writable roots of the turn's sandbox policy, alongside the agent home and the board projection.

### Codex is not isolated from the account's own configuration

It reads `~/.codex/config.toml` and its login from the default home; the model comes from there unless the agent record sets one. It also loads the account's global `~/.codex/AGENTS.md` as instructions: in the Phase 8 live run the Codex referee of a research study required a uv project, Ruff, pre-commit hooks, a README, and an AGENTS.md, citing them as the user's requirements, because they were the account owner's personal coding rules. The Claude adapter loads project settings only, so its agents do not see `~/.claude/CLAUDE.md`. The rendered instructions travel as the thread's developer instructions, set again on every start and resume.

### The Codex app-server bindings are generated on demand

The Codex app-server bindings are generated on demand, with `codex app-server generate-ts --out packages/adapter-codex/src/generated --experimental`, and are not committed: the adapter reads the few fields it needs by hand, and the recorded turns in `packages/adapter-codex/fixtures` fail when a release changes them.

### A Codex web search fills in as it runs

Its `item.started` carries an empty `query`, and a search opened by URL or run from code keeps it empty, with what it did in `action` (a search with `queries`, `open_page` with a `url`, `find_in_page` with a `pattern`). The adapter reports the call when the item completes and describes it from the query or the action; reported at start, every search in the live transcript was blank.

## Usage, cost, and models

### Token counts are a turn's own, and both CLIs report them as something else

Codex's `thread/tokenUsage/updated` carries the thread's running `total` and the `last` request alone; the adapter once kept `last`, so a turn of five requests recorded only the fifth, about a fifth of what it used (30,630 input tokens of 151,361 in the recorded steered turn). The session now keeps the thread's latest total from every update, and a turn counts what the total grew by from where it stood before the turn: a resumed thread reports its saved total, about its previous turn, before the turn starts, and an update about another turn, or before the turn has an id, which `turn/started` gives it in stream order, sets that starting point. Codex also counts cached input inside `inputTokens`, while Claude Code counts it apart, so the Codex adapter subtracts it and `Usage` means the same on both CLIs: `inputTokens` is the input neither read from the cache nor written to it. A Claude result's `usage` counts only its own run's main loop, and a cold turn can run more than once in one process, for a steer the CLI took after its result or for a background task a resumed session reports first, so the adapter adds the results up, where it once kept the last run's alone; that sum is now only what a turn falls back to, since a Claude turn counts what the session's `modelUsage` grew by (next section). `turn.completed` and `turn.failed` carry `usage` from then on; turns logged before have none, and the Codex counts kept before in turn records and transcripts are the last request's.

### A Claude turn counts what the session's `modelUsage` grew by

A result's `usage` leaves out a sub-agent's requests and the CLI's own calls; the Agent SDK's types say so (`MAIN AGENT LOOP ONLY`), and against a local stub of the Messages API on Claude Code 2.1.283 a turn whose Agent tool ran a sub-agent of 7,000 input and 70 output tokens recorded only its four main-loop requests' 400 input, 200 output, and 8,000 cache-read tokens. `modelUsage` counts every request of the query, per model: the main loop's, the sub-agents', and the CLI's own, such as the title request with no tools it makes for each prompt of a query that started the session. The adapter sums it over the models (`sessionUsageOf`), cached input apart as in every `Usage`, and a turn counts what it grew by, never less than nothing in any count (`turnUsage`); that turn then counted 7,430, 273, and 8,000, what the stub answered. `total_cost_usd` covers the same requests: it equalled the sum of `modelUsage`'s per-model `costUSD` on every result recorded, two models included, so a turn's tokens and its cost count the same requests.

`modelUsage` runs as the cost does: it is cumulative within a query, and a resumed session starts from the totals its transcript saved. Claude Code writes them into the session's own transcript as a `cost-state` entry only when its process ends, once for all the turns it ran, so another session run in the same folder in between changes nothing. So the board keeps it beside the cost. The outcome reports the session's latest totals as `sessionUsage`, the turn record keeps them, and the host hands them to the session's next turn as `usageSoFar`, under the cost's rule: only when the last record names the session being resumed. A warm session keeps its own between turns. A result whose `modelUsage` names no model reports none, as the one Claude Code writes before any init message for a resume it could not make.

- **What a session spends between turns.** A cold turn's CLI runs on until its background sub-agents end, and the runs their ends start, within the turn's limit, so the turn counts them. A warm turn ends at its prompt's result, so what a sub-agent still running then spends, and the run its end starts, counts in the next turn on the session: on a warm session whose sub-agent answered between turns, the next turn counted the sub-agent's 7,000 and 70 and that run's two requests with its own, and the turn after only its own. What a session spends after its last turn counts in no turn, and a request still unanswered when its process ends is in no saved total, as a sub-agent's was when its cold turn timed out.
- **A turn that saw no result**, because it was stopped, timed out, or failed before one, counts what it did before, nothing, and so does one that never reached its CLI, as when its runner could not pull the board's copy or prepare its workspace. For every turn whose outcome reports no running usage, the runner reports the job's `usageSoFar` as the session's (`daemon.ts`, `runJob`). A kill at the turn's limit lets Claude Code save its totals as its process ends, with what was answered before, so the session's next turn counts that, as its cost already did: a cold turn killed in a tool after one answered request counted nothing, and the next turn counted that request with its own.
- **A CLI killed outright**, by a SIGKILL as the out-of-memory killer sends, saves nothing of the turns its process ran, so the next resume starts from older totals, below the board's `usageSoFar`. The turns it ran counted their own already, except one it cut short, whose answered requests count in no turn; the next turn's first result shows the shortfall, since the session held at most that result's running usage less its own run's `usage` before it (`heldBefore`). When that falls below `usageSoFar` in any count, the turn counts the sum of its results' `usage`, as with no running usage on the board, and its `sessionUsage` is what the CLI holds now. On a warm session of two turns whose CLI was SIGKILLed, the cold resume after counted its 100 input, 50 output, 2,000 cache-read, and 10 cache-write tokens this way, where measuring from the board's figure counted nothing, and the turn after measured its 7,400 with a sub-agent exactly. A first run whose sub-agents and side calls outweigh what was lost hides the shortfall, and the turn then counts that much less. A SIGABRT or a SIGSEGV saves nothing either, and the tokens fall back the same way. The cost has no such fallback; [AGENTS.md's technical debt](../../AGENTS.md#technical-debt-known) gives the exact case.
- **A resumed session with no running usage on the board** counts the sum of its results' `usage`, the main loop alone, never the session's whole total: a record from before `sessionUsage`, a last record of another session, and a job from a server from before, which sends no `usageSoFar`. Its own `sessionUsage` gives the next turn one. A runner from before sends no `sessionUsage`, and the host records only what the outcome says, so a record holds a running usage only from a runner that keeps it; either can be updated first.

### A resumed Codex thread may report no totals, and a turn then takes them from its own first update

The starting point comes from Codex: right after `thread/resume`, its app server sends a `thread/tokenUsage/updated` about the thread's previous turn with the saved total. It does not always come. codex-cli 0.158.0 and 0.162.1 send it to a resume with `excludeTurns`, which the adapter asks for to keep the thread's history out of the response, only for a `paginated` thread, the history mode a new thread gets since 0.151.0 where Codex's SQLite state database is available; a `legacy` thread gets it only from a resume that takes its turns (`token_usage_turn_id` in `thread_processor.rs`). And on 2026-10-23 a live 0.158.0 sent none for a paginated thread whose previous turn had ended normally, for a reason not found. With no total the starting point stayed at zero, so a turn counted the thread's whole history as its own, and a turn the model service refused before any request counted it too, since Codex sends the thread's total for the failing turn when the refusal carries rate limits.

So when no total came before a turn's first update of its own, that update sets the starting point: the thread's total less the request it reports (`last`) when the model has answered in the turn, and the total as it stands when it has not, as with an update that only carries rate limits. The model has answered once an item its answer made has started (`answered`): Codex starts a request's items as its answer streams, before it reports the request, while a command that outlives its yield completes only after that report, or never within the turn, so a completion would come too late. Items Codex or the user makes are no answer (`NOT_ANSWERS`): the prompt and steers, a tool output a client starts a turn with (`functionCallOutput`), a hook's prompt, review mode, a compaction, which Codex starts before its own request, as a refused one does too, and a sub-agent's activity (`subAgentActivity`), which reports a sub-agent's turn ending under the parent's turn that started it, while a later one may be running. Nor is an item under another turn's id: on a warm 0.162.1 session, a command the model left running in one turn completed in the next under the turn that started it. On the recorded 0.156 resume with that update removed, this gives the same 252 input, 85 output and 18,304 cached tokens as with it, and on the recorded steered turn resumed without its totals or its opening message, whose first request's only item is a running command, the same 5,313 input and 146,048 cached as with them. And whatever the totals say, a turn the model never answered counts nothing: Codex also moves the totals without an answer, as when it fills them to the context window for a turn that ran out of room (`fill_to_context_window`). Measured against a local stub of the model service on 0.158.0 and 0.162.1, with legacy and paginated threads, and with and without rate-limit headers: every working turn counted its own 600 input, 50 output and 400 cached tokens, and every turn refused before any request none, where the adapter had counted a legacy thread's whole history, 1,200, 100 and 800, for both. A turn whose first request answered with a command still running when the next one was refused counted that request, 600, 50 and 400, and a legacy resume whose first request did the same counted both of its requests, 800, 80 and 1,400.

### The Codex app server sends a connection every thread it runs, a sub-agent's too

The app server attaches each connection to every thread it creates (`try_attach_thread_listener`, codex-cli 0.162.1), so a sub-agent the model spawns, with `multi_agent`, on by default, or `multi_agent_v2`, sends its own turn, items, totals, and failures to the parent's connection under its own `threadId`. The adapter once read them as its own thread's. A sub-agent's totals became the parent turn's starting point, so a parent turn whose sub-agent answered while it worked counted 0 input and 80 output tokens of its 1,800 and 150 with `multi_agent`, and 0 and 30 of 1,200 and 100 with `multi_agent_v2`, against a local stub of the model service. A sub-agent's message could also become the parent's status object, and its failure the parent turn's. The adapter now reads none of another thread's turns, items, or failures, only a sub-agent's totals, which count as the next section says; the plan's rate limits name no thread and stay the account's.

### A Codex sub-agent's requests count in the turns of the thread that started it

A sub-agent works on the parent's behalf, and its totals are its own: no thread's `thread/tokenUsage/updated` includes its sub-agents'. So a turn counts its thread's growth and each sub-agent's growth since a turn last counted it (`subAgentUsage`).

- **Which threads.** This thread's sub-agents and theirs, and no other. codex-cli 0.162.1 sends no `thread/started` for a sub-agent and puts its `parentThreadId` in no notification; an item on the thread that started or addressed it names it instead: a v1 `collabAgentToolCall`'s `receiverThreadIds`, which a spawn fills only on `item/completed` and `resume_agent` from the start, or a `multi_agent_v2` `subAgentActivity`'s `agentThreadId`, since v2 sends no collab item for a spawn. A parent's items and a sub-agent's notifications come from separate listener tasks in no set order, so a thread named by one not yet known to be a sub-agent waits for it. An app server attaches only the threads created or loaded in its own process, so another session's thread reaches the connection only when this session's model loads it, as v1 `resume_agent` does for any id in the shared store; this session's item names it then, and it counts here. Codex's own threads, such as memory consolidation, are never attached.
- **From where.** The first update the app server sends of a thread reports one request, before which the thread stood at zero if new, at its saved totals if resumed, since Codex replays no totals for a sub-agent it resumes or reloads, and at its parent's if forked from a `legacy` thread. So a sub-agent starts from its first total less that update's `last`.
- **When.** A turn counts what its sub-agents grew by until it ends. A sub-agent keeps working after the parent's turn ends: on a warm session what it spends then counts in the next turn, and once the session has closed in none. A cold turn stops its app server, and the sub-agents in it, as it ends.

Measured on codex-cli 0.162.1 against a local stub where each parent request is 1,000 input (400 cached) and 50 output, a sub-agent's 7,000 and 70, and a nested one's 3,000 and 30, each turn counted what the stub answered: 8,800 input outside the cache, 220 output, and 1,200 cached for three parent requests and a `multi_agent` sub-agent's one; 8,200, 170, and 800 for two and a `multi_agent_v2` sub-agent's one; and with `[agents] max_depth = 2`, 18,800, 320, and 1,200 for three, a sub-agent's two, and its own sub-agent's one. Before, each counted the parent's alone. On a warm session whose sub-agent answered between two turns, the second counted its 7,000 and 70 with its own 600, 50, and 400, and the third only its own.

### A turn reports how large its session had grown, apart from what it used

The outcome's `contextTokens` is the whole input of the turn's latest request in the session's own thread, cached or not: what the session's next request starts from, less that request's output. The turn record and `turn.completed` keep it, and the scheduler reads it against `sessionCapTokens` (see [a society role's home](conversations.md#a-society-roles-home-starts-afresh-after-each-reflection)). `usage` and `sessionUsage` cannot say it, since they sum every request, so a turn of thirty requests counts its context thirty times.

- **Claude Code.** Each assistant message carries its request's `usage`, and the adapter takes the newest one whose `parent_tool_use_id` is null, as its input, cache-read, and cache-write tokens together. A sub-agent's messages are another context. A message the CLI writes itself, as for a 400 the API answered, carries zeros, which are skipped. A request that sampled several times, as server-side tools loop, sums its samples at the top level; the SDK's `BetaUsage` says to read a context's size from the last `message` entry of its `iterations`, which the adapter does when one is listed. On the review turn recorded from Claude Code 2.1.283 the last request read 2, 27,995, and 974 tokens, 28,971 in all, and the result's last iteration said the same.
- **Codex.** `thread/tokenUsage/updated` carries `last`, the latest request alone: in the recorded 0.156 turns each update's `total` grew by exactly its `last`. The adapter takes `last.inputTokens` of the newest update of its own thread for its own turn, since Codex counts the cached input within the input; an update about the thread's previous turn, as a resumed thread sends first, or about a sub-agent's thread is no measure of this one. The recorded steered turn's five requests ended at 30,630. Codex reports the model's window beside it, `modelContextWindow`, which depends on the model: 258,400 for `gpt-6-astra` in those recordings, 475,000 for `gpt-6.1-sol` in the 0.162.0 quota recording. So the default cap of 300,000 can fire on Codex only for a model whose window is larger than it.

A turn that made no request reports none, and a runner from before sends none, so the scheduler then asks nothing.

### The model is observed, not assumed

Turn records carry the model the CLI reported: Claude Code names it on the session's init message, the Codex app server on the response that opens the thread. Until every Codex turn ran over the app server, cold Codex turns through `codex exec`, whose stream never names it, fell back to the configured model and showed "cli default" when there was none. The roster keeps both the configured `model` and the `lastModel` observed, and the front desk's digest prefers the observed one.

### Costs

With the default model, observed Claude turns cost between a tenth and a third of a dollar; a full two-agent task with review ran about one dollar. Codex reports tokens but no price, so its turns are recorded at zero cost until a price table exists, which the tokens each turn records are enough for; they are not free, only unmetered, so a wasted Codex turn is a real cost. Set `STELLARIS_LOG_LEVEL=debug` to see every tool call and the CLI's stderr in the server log.

## Refusals

### A turn the model service turned away for now is transient

Each adapter marks a turn `transient` when it failed on the model service's side after the CLI's own retries ran out, and the scheduler sends its wake again within minutes (see [wakes](conversations.md#a-turn-the-model-service-turned-away-goes-again-within-minutes)). A plan's usage limit is not transient: the CLI is held off until the window resets (see [plan quota](runners.md#a-clis-quota-is-what-its-login-reported-kept-on-its-runners-record)). Nor is a refusal for the context window, a policy, a sign-in, or any other 4xx, which a minute does not cure. The runner keeps the mark only on a turn that ended `error`, and the turn record and `turn.failed` carry it.

Codex names the failure in `codexErrorInfo`, on the `error` notification it sends without `willRetry` and on `turn/completed`. "Selected model is at capacity. Please try a different model." is Codex's own words for `serverOverloaded`, which it gives a 503 or a failed stream with the code `server_is_overloaded`; it retries that only at the HTTP layer, four times by default, unless the service sent `Retry-After`. Transient are `serverOverloaded`, `internalServerError`, `rateLimitExceeded`, `flexUnavailable`, and the four codes that carry `httpStatusCode` when it is absent, 429, or 5xx (`isTransient`). Against a stub on codex-cli 0.162.1: a 503 overload failed the turn after five requests in 3 s, a 500 after thirty in 25 s as `internalServerError`, and a 429 at once as `responseTooManyFailedAttempts` with its status.

Claude Code ends a turn the API refused as a `success` result marked `is_error`, with `api_error_status`; the adapter marks a 5xx or a 529 transient, or, with no status, an assistant message whose `error` is `server_error` or `overloaded`. Claude Code 2.1.283 gives up on a 529 after three requests in about 2 s, saying "Repeated 529 Overloaded errors", and on a 500 after eleven over three minutes, both with `error: "server_error"`; a 429 it retries as long and then reports as `rate_limit`, which the adapter reads as the plan's limit.

## Recorded streams

### Recorded streams are fixtures

`STELLARIS_RECORD_DIR` makes both adapters append each turn's raw stream to a file. Scan a recording for token-like strings before committing it under `packages/*/fixtures`; the streams carry tool outputs, not credentials, but check anyway.

## History

### A Codex turn the model service refused once waited a quarter hour and counted a whole conversation

On 2026-10-23 a Codex citizen's turn on a mention failed in 7 s with "Selected model is at capacity", and so did its heartbeat a minute later, while another citizen on the same runner and model completed a turn: nothing ran the mention again until the user asked seven minutes later, where otherwise the next heartbeat would have, up to a quarter hour after the first failure. The failed turn was recorded with 361,546 input and 54,377 output tokens, the sum of the eight turns before it in that conversation, which is what a turn records when its thread reported no starting point (see [resumed threads](#a-resumed-codex-thread-may-report-no-totals-and-a-turn-then-takes-them-from-its-own-first-update)). Such a turn is now [transient](#a-turn-the-model-service-turned-away-for-now-is-transient), goes again after a minute, and counts nothing.

### A turn the plan's limit refused once said nothing of the limit

On 2026-10-12 a runner's Claude login met its 5-hour limit, and between 10:13 and 10:57 UTC thirteen turns of the front desk, the reviewer, and the developer each got only Claude Code's synthetic message, "You've hit your session limit · resets 11am (UTC)", with no status object, as the CLI's transcripts show; the adapter read no limit from it, so each turn ended as one without a report would, and nothing on the board named the limit or when it lifted. Such a turn now fails with the CLI's words and reports the limit (see [plan quota](runners.md#a-clis-quota-is-what-its-login-reported-kept-on-its-runners-record)). The two CLIs' numbers come in different units: Claude's stream gives each window's `utilization` as a fraction of one, its usage read as a percentage, and Codex's both as percentages; a live turn and a read a minute apart on that runner gave 0.15 and 15 for the same window.
