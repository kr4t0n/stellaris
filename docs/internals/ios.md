# The iOS client

How the native client's code is laid out, how the app signs in and keeps its place, how it stays in step with the server, and how it is tested. [AGENTS.md](../../AGENTS.md) states the rules in short, and the commands are in the [README](../../README.md#run-build-test).

## Layout

### `apps/ios` holds the app, BoardKit, and their fixtures

`apps/ios/BoardKit` is a Swift package, BoardKit, for the board's API: Swift 6, for iOS 27.0, and macOS 15 so `swift test` runs on a Mac. Its one dependency is Apple's swift-markdown, held at 0.9.0 in `Package.swift`, with `Package.resolved` committed; the app's `project.yml` holds swift-markdown's own dependency, swift-cmark, at the version that file pins, since the generated project resolves its packages afresh. `apps/ios/Stellaris` is the SwiftUI app, for iPhone on iOS 27.0, with its unit tests in `StellarisTests` and its UI tests in `StellarisUITests`. `apps/ios/fixtures` holds what the tests read beside the server's and the web's: `api/`, the answers the server's tests capture, `cases/`, the case tables of the ports, and `sky/`, the tables the web's sky tests write for the sky's port. `apps/ios` has no `package.json`, so pnpm and the TypeScript build leave it alone.

### XcodeGen writes the app's project

`apps/ios/project.yml` names the app's targets, its scheme, its `Info.plist` and its entitlements, and `xcodegen generate` in `apps/ios` writes `Stellaris.xcodeproj` and the two plists into `Generated/`, none of which is committed, so the project never drifts from the spec or carries one person's Xcode settings. `ios.yml` installs XcodeGen 2.46.0 from its release, checked against the digest GitHub lists for the asset.

`Config/Stellaris.xcconfig` holds the three settings that name an Apple developer account and a board: the bundle ID, the team, and the host of the board the app signs in to with GitHub. Its values build for the simulator with no team. A build for a device sets its own in `Config/Local.xcconfig`, which the file includes when it exists and git ignores; `Local.xcconfig.example` shows the three. The host goes into the app's `Info.plist` as `StellarisBoardHost` and into its associated domains as `webcredentials:<host>`. [Running the iOS app on an iPhone](../guide/ios-device.md) takes a device build from the Mac's setup to signing in.

### The app's icon is an Icon Composer document

`apps/ios/Icon/AppIcon.icon` is the app's icon, a document of Icon Composer, the icon tool that comes with Xcode: `icon.json` holds the background and the layers' order and settings for each appearance, and `Assets/` holds one SVG per layer on a 1024-point canvas, unmasked, the three meteors in a group behind the three stars. Each appearance's fill is an entry of a `fill-specializations` list, the default's the entry with no `appearance`, as Icon Composer writes them: the background is a vertical gradient in the default appearance and a darker one in dark, and in the clear and tinted appearances the three stars fill solid white while the meteors keep their own colours, which the system makes monochrome. A `fill` beside the list, at the top or on a layer, leaves the list unread: Dark drew on the system's neutral gray, and the stars kept their shading in Clear and Tinted. A solid fill also replaces a layer's own transparency, so the meteors take none: with one, their tails drew at full strength from end to end instead of fading. The system draws the mask, the glass, and the clear and tinted backgrounds. `project.yml` puts the document among the Stellaris target's sources, which XcodeGen files with the resources as an Icon Composer wrapper from 2.45.1 on, and names it as the app icon (`ASSETCATALOG_COMPILER_APPICON_NAME: AppIcon`). So the asset compiler builds it into the app's `Assets.car`, writes `AppIcon60x60@2x.png` and `AppIcon76x76@2x~ipad.png` beside it, and names `AppIcon` as the primary icon in the `Info.plist`. `AppIconTests` checks that name and loads the pictures the entry names, since `UIImage(named: "AppIcon")` finds nothing for an Icon Composer icon.

To change the icon, open the document in Icon Composer (Xcode > Open Developer Tool > Icon Composer) and save it there, or edit an SVG or `icon.json` by hand, then build. Icon Composer writes `icon.json` with its keys sorted and a space before each colon, which `.oxfmtrc.json` keeps the formatter away from (`apps/ios/Icon/**`), so a hand edit keeps that style. SVG colours with no colour space of their own are read as sRGB while `icon.json` has no `color-space-for-untagged-svg-colors`, which is how it is kept: set to `display-p3`, that key reads them as Display P3, and with it set to `srgb` Xcode 27.1's asset compiler refuses the document ("Icon export exited with status 255"); the public Icon Composer documents sampled on 2026-11-07 set it only to `display-p3`. `ios.yml` draws the icon in iOS's six appearances, Default, Dark, Clear Light, Clear Dark, Tinted Light, and Tinted Dark, with Icon Composer's own `ictool`, into the `screens` artifact's `icon/` folder, so a pull request that changes it shows what the system draws. The Home Screen and the icon at its smallest sizes are on the device's list.

The web's `apps/web/public/favicon.svg` flattens the Default background and six SVG layers, preserving their geometry, gradients and opacities, with the web's existing rounded corners (7/32 of the canvas). When changing the app icon, update this static favicon, its rasters and `manifest.json` too; `apps/web/src/favicon.test.ts` checks its background against the Default fill and its artwork against the source layers. `index.html` links the SVG, 16/32 px PNG fallbacks, the 180 px Apple touch icon and the manifest. The 16/32/48 px ICO stays at `/favicon.ico` for clients that discover it by convention, without a link. Chromium 153 selected the ICO over the SVG when an ICO link declared all three sizes; removing that link kept the SVG at device scales 1, 1.5, 2 and 3. Keep the ICO unlinked to preserve that selection. The PNG sizes cover small and double-density icons where a browser chooses PNG; they did not win over the SVG in those Chromium checks. The touch icon alone has opaque, square corners: [Apple's icon guidance](https://developer.apple.com/design/human-interface-guidelines/app-icons) leaves masking to the system, and its [Safari guide](https://developer.apple.com/library/archive/documentation/AppleApplications/Reference/SafariWebContent/ConfiguringWebApplications/ConfiguringWebApplications.html) documents the 180 px link. The manifest names Stellaris, uses the ground's top colour for `theme_color` and bottom colour for `background_color`, and links 192/512 px PNGs with purpose `any`; the artwork is not designed for maskable cropping. It omits `display`, preserving the browser default rather than opting into standalone. The server already serves `.json` as JSON; no manifest-specific route is needed.

After updating the SVG, regenerate the rasters from the repository root with the pinned Playwright Chromium (no build step or extra dependency):

```bash
pnpm --filter @stellaris/web exec playwright install chromium
node apps/web/scripts/generate-icons.mjs
```

The script prints a fresh temporary directory containing the six raster files. Copy those `.png` and `.ico` files into `apps/web/public/`, inspect them at their native sizes, then remove the temporary directory. `node apps/web/scripts/generate-icons.mjs --check` renders the complete SVG again and compares every raster byte, including the ICO frames; run it with the same pinned Chromium after a source or browser-version change. `pnpm exec vitest run apps/web/src/favicon.test.ts apps/web/src/favicon-assets.test.ts` checks source artwork, HTML links, PNG/ICO dimensions and manifest references and colours. The Apple icon's opacity is also checked during generation. CI checks the links and dimensions but does not run the Chromium-dependent raster byte comparison, so the regeneration check remains a manual step.

### BoardKit's core is Foundation alone, and its transport is Apple's

The core builds and tests on Linux with swift.org's toolchain: the models (`Models.swift`), the request builders (`Requests.swift`), the board's refusals (`BoardError`), the server-sent-events parser (`ServerSentEventParser`) and the follower that reads the board's event stream across drops (`EventFollower`), the app's GitHub sign-in (`AppSignIn`: the verifier, the landing's address read, and base64url), the ports of the web's `staleKeys` and `needsYou`, the port of the sky's model and camera (`SkyModel.swift`, `SkyCamera.swift`), the port of the sky's scene, its motion and what each frame draws (`SkyScene.swift`), with the CLI marks, the theme's colours, and a reader of SVG path data (`SkyMarks.swift`), the live turn stream's events with the web's `postedLine` (`LiveTurns.swift`), the web's `withTitles` and `splitEntities`, which read ids in a line as what they name (`Titles.swift`), a message's markdown as the blocks the app draws (`MessageMarkdown.swift`), the web's rules for where a link goes (`Links.swift`), the web's palette and sizes for a message (`MessageTheme.swift`), the mention being typed in a draft (`Compose.swift`), a channel's stream of messages and threads, with a closed thread's summary as the web's `firstParagraph` gives it (`ChannelStream.swift`), a proposal's charter read as its kind and said in one line, as `describeCharter` says it, with the web's `proposalTitle` and `decidersOf` (`Charter.swift`), and what the web's task views say of a task and its plan (`TaskPlan.swift`). `Transport/` holds what needs Apple's frameworks, compiled only where they exist: `BoardClient`, the API over `URLSession` with the bearer token, a connection to the event stream (`eventConnection`), which hands over the board's answer, its events, and its pings, and the turn stream, images, and the sign-in's code trade; the sign-in's S256 challenge, with CryptoKit; and `TokenStore`, the token in the Keychain. Linux's Foundation has no `URLSession.bytes(for:)`, which the two streams read with, no SHA-256, and no Keychain.

### The models hold what the app reads of the shared schemas

Each model holds the fields of its schema in `packages/shared` that the app reads, under the same names, and decodes a field the schema defaults with the same default. Ids and times stay the strings the board sends, since both sort as text.

The app is installed apart from the server and falls behind its releases, so a value the server adds must not fail an answer, as one invalid item fails a whole list in the web, which the server's own build serves. A value of a closed set, such as a task's status, is an `OrUnknown`: one of the enum's cases, or `unknown` with the raw value, which a view can show as it is. `TaskPhase` has an `unknown` phase for a status the app doesn't know, whose stage waits on nobody, and a proposal of a kind it doesn't know waits on the user, who decides every kind the board has had. The two unions of a message do the same for a shape: a `MessageStep` that is neither a task's step, which names its stage, nor a proposal's, which names only its action, and a `MessageNotice` of a kind other than `knowledge`, or one whose fields don't read as a knowledge topic's, decode as `unknown` with their fields as sent. An event's type stays a string, so an event a newer server adds touches no read. A proposal's charter is read as its kind's schema reads it (`Charter`), all or nothing, but for a value of a closed set the board may grow, a CLI, a verb, or a wake, which reads as it is, so a role that grants a verb a newer board added keeps its line. `UnknownValueTests` decodes captured answers with one value or one step or notice changed to one the app doesn't know.

A model whose name Swift or Foundation already uses takes a `Board` prefix: `BoardTask`, `BoardThread`, and `BoardActor`.

### The request builders name every request the app makes

`BoardAPI` builds each read and each verb the app makes as a `BoardRequest`, which knows its answer's type, a file on a task's branch among them, and the event stream and uploaded images as an `Endpoint`, whose answer is bytes. A verb goes to `POST /api/verbs/:verb` with its input's fields named as the verb's schema names them, and a field left empty is left out. Each part of a path is encoded as the web's `encodeURIComponent` encodes it, and a board's address may end in a path of its own. `/auth/config` and the app's sign-in, its start and its code trade, are asked without the token. A refusal is `{error, message}`, or `{error}` alone from the code trade, which answers as OAuth does.

## The app

### Sign-in takes the board's address, then GitHub or a token

The address is `https` only, since every request carries the token; a host alone is taken as `https://<host>`, and a path the board is served under is kept (`BoardAddress`). The app then asks the board's `/auth/config`, and where nothing answers at the address it stays there and says it can't reach the board (`BoardClient.authConfig` throws `BoardError.unreachable`). It offers GitHub where the board answers `github` and `appLanding` and its host is the one the build names, since iOS hands an `https` callback only to an app associated with the host it is on; anywhere else, a board that answers without saying included, as one from before GitHub sign-in, it takes a token alone.

GitHub's sign-in is the board's app landing ([GitHub sign-in](./runners.md#github-sign-in)) with PKCE. The app makes a verifier (`AppSignIn.makeVerifier`), opens `BoardAPI.appSignIn(challenge:)` in SwiftUI's `WebAuthenticationSession` with the callback `.https(host:path:)` on the board's host and `AppSignIn.landingPath`, in the shared browser session so a GitHub login in Safari carries over, reads the address it lands at (`AppSignIn.landing`: a code, or the board's reason for refusing), and trades the code with the verifier at `/auth/app/token` (`BoardClient.appSession`). iOS ends a session it won't start, as for a callback host it hasn't associated with the app, with the same `canceledLogin` as the person's cancel, before showing anything, and with its reason in the error, so the app shows that reason under the form and stays silent only for a cancel that carries none (`AppSignIn.refusal(ofCanceled:)`). A token pasted from the board goes through the same last step: the app keeps a token only once `/api/me` takes it, in the Keychain under the board's address (`TokenStore`), and the address in its defaults.

Once signed in, a 401 on any request drops the token and returns the app to sign-in, saying the board ended the sign-in. `AppModel` counts sign-ins and sign-outs (`generation`), so what comes back for an earlier sign-in changes nothing: a 401 for its token ends nothing (`AppModel.send`), and what its loads bring back, the board's lists, a failure, or who the token signs in as, is dropped (`BoardStore.refresh`, `AppModel.refresh`). Each conversation's messages live in a feed that signing in or out replaces, so a late answer lands in one nothing shows. Signing out ends a GitHub sign-in on the board too (`DELETE /api/sign-in`), drops the token, and forgets the drafts.

On the inner display folded like a book, the sign-in form moves off the fold: `SignInLayout` takes the fold's frame from `reservedRegions(kind: .division)`, which iOS 27.1 reports, and gives the form the wider side, the trailing one when both are as wide, or above a fold that runs across. Beside it, only the inner display's split reads reserved regions; the system's containers move out of a fold by themselves.

### One scene of three tabs

The app has one scene (`UIApplicationSupportsMultipleScenes` is false), whose one window resizes with the display it is on. It is dark only, as the web is: `UIUserInterfaceStyle` is `Dark` in its Info.plist (`project.yml`), so iOS draws every window of the app dark, sheets and the snapshot harness's windows included, whatever the system's setting. Views use the system's semantic colours, which take their dark values, but for a conversation, which is drawn as the web draws one (below), and the grounds of Board's, Needs you's, and Settings' lists: they sit on the conversation's island gray, as the web's board views sit on the island the conversation does, with a grouped list's rows on `surface-2` at 50% over it, which blends to 29 in each channel, the tone of the web's row under the pointer and of its composer's box, so each section reads apart from the gray around it; a project's list at the accessibility sizes, which is plain, has its rows on the island itself, as the web's rows are (`islandList`, `islandRow`). As that list scrolls, a section header pins at its top over the rows going under it, and iOS draws its hard scroll edge effect, the nearly opaque boundary its `automatic` style gives pinned content over scrolling content, from the bar to the header's foot: the island blurred, about 28 to 32 in each channel, with the island again below it. The app keeps the system's boundary rather than drawing a ground of its own behind the header and the bar. Of the web's two tones for a row, under the pointer and current (`surface-2` at 80%), it is the one at which the system's blue keeps WCAG AA's 4.5 for text on a row (4.62, against 4.36 at 80%), and the system's text colours, which the lists keep, read at 16.86 for the label and 5.95 for the secondary label there. A row background of the app's own hides the one the list draws for a pressed or a selected row, so each row's ground follows its list cell's `isHighlighted` and `isSelected` and takes the system's own highlight, `systemGray4`, while the cell is either, as the system's rows do, coming on at once and fading back to rest over a quarter of a second (`RowGround`). Its root is a `TabView` of Chat, Board, and Needs you, each with its own navigation stack, and Needs you's badge counts what waits on the user. On a compact width iOS draws the tab bar in the side bar, where a tab shows its icon alone. The icons are outlines, as Safari's side bar draws its own, since each tab's label sets `symbolVariants` to `.none` where a tab bar would fill them, and Chat's is one bubble (`bubble.left`), as wide as the others; on the inner display in portrait, where the bar runs along the foot, iOS's default words under the icons stay. Every button in a bar, a sheet's and the image viewer's included, is a `Label` with a title and a symbol: on the outer display iOS moves a bar's symbols into the side column at the window's trailing edge, below the status bar's clock, and keeps a text-only button in a bar across the top, which ends about 88 points short of that edge, where the column begins (Apple's iPhone Duo guidelines, "Vertical controls"). A sheet that only shows something, the plan's or the charter's and Settings, has no button and closes with a drag down, as Apple's sheets guidance keeps Done for a sheet that completes a task or saves a change; Settings shows its grabber, and the plan's sheet has one for its two heights. The image viewer, a full-screen cover, which can't be dragged away, has Close, an ✕ in the cancelling place, drawn plain as Cancel is rather than in the confirming tint.

Chat holds the conversation, a channel or a thread. Board lists the society's channels, then each project's dashboard and tasks, its channels, and its tasks in play, and Needs you lists what waits on the user as the web does; picking a channel, a task, or what waits opens it in Chat (`AppModel.open`), where a proposal or a stage has the actions that decide it (below). Each shows the board's state, loading, failed with Retry, or empty, only while it has no rows (`BoardState`): once they have loaded, a refresh that fails leaves them as they were, as a conversation does its messages. Back in Chat goes to the conversation Chat showed before, as the web's back arrow follows where the user came from, up to 50 steps (`ChatHistory`); a thread with nothing before it goes back to its channel. Settings, in a sheet from Board, shows the board's address and who the app is signed in as, and signs out.

### A message is drawn as the web draws one

A conversation sits on the web's island: `surface-1` at 80% over `surface-0`, which the browser blends to a gray of 20 in each channel (`MessageTheme.island`), and each message is laid out as the web's `MessageItem`: its author's tile beside the name and when, over its text, the board's own posts dimmed. At the accessibility type sizes the tile sits beside the name, the time wraps under it, and the text takes the row's whole width. The tile is a citizen's CLI mark on `surface-2`, the user's GitHub picture or "you", or the board's ✦, as the web's `Avatar`; the name is the user's GitHub login, or "you", as the web's `displayName`; and when is the web's `ago`, "3 minutes ago", "yesterday", or "just now". The type is the web's: Instrument Sans, whose six faces (regular, medium, and semibold, each with its italic) are in `Stellaris/Fonts` beside its licence, the SIL Open Font License 1.1, and listed in `UIAppFonts`, at `text-sm`, 14 points, for names and text and `text-xs`, 12, for times and tables, each scaling with Dynamic Type from there (`Font.custom(_:size:relativeTo:)`), with lines as far apart as `leading-relaxed` sets them; code is the system's monospaced face at the caption's size, 12 points by default, as the web's is. The grays, the text colours, and the mention's colours are the web's tokens in `MessageTheme`, which `MessageThemeTests` reads `styles.css` to check.

BoardKit reads a message's markdown into `MessageDocument`, as the web's `Markdown` component reads it: swift-markdown parses it with GitHub's tables, strikethrough, and task lists, with quotes and dashes kept as written; GitHub's literal autolinks, which swift-markdown leaves as text, are found as `mdast-util-gfm-autolink-literal` finds them, `http://`, `https://`, and `www.` addresses, then mail addresses; then the ids of what the board names, tasks, proposals, threads, and messages from `BoardStore.entities`, read as links named by their titles, as the web's `remarkEntities` reads them, a code span holding nothing but a known id included, and a message's as whose post it is and where, "eng-1's post in #general", with "message" or "post" and whose right before it dropped; then `@name` marked as the board's mention pattern finds it, outside code and links. The text of a link, even one that goes nowhere, and raw HTML, which shows as written, are never read for addresses, ids, or mentions, and raw HTML stays apart from the text around it, so an address before a tag ends at it. An image's description reads code's words without its backticks. The autolinks follow the transform's rules alone, not micromark's literals, which the web and GitHub run first: `1http://a.bc` stays text where both link `http://a.bc`, an address whose host has no dot, such as `http://localhost:5173`, stays text where both link it, and `https://a.bc/&lt;x` links with `<`, since swift-markdown hands its text over with entities decoded, where the web keeps `&lt;`. An address with a scheme other than `http`, `https`, `irc`, `ircs`, `mailto`, or `xmpp` is dropped, as `urlTransform` drops it, which leaves its text.

SwiftUI draws each block (`MessageBody`), the text of each an `AttributedString` in a `Text` (`MessageText`). A code block never wraps: it scrolls sideways, and a long press offers to copy it. A table scrolls sideways when it is wider than the column, each cell wrapping at 240 points (`CappedWidth`), with the web's hairlines between cells. A link to a task, a proposal, a thread, or a message opens it in Chat (`AppModel.follow`), a link to a cron or a file on a branch opens the board's own page for it in Safari, as does an address on the web, and a path on a runner's machine reads as text. An image loads by where it is (`BoardImages`): one a citizen uploaded with the token, kept by its id for as long as the sign-in lasts, since an upload never changes; one on a task's branch, which the board reads from the project's runner; and one on the web over `https`, without the token. It shows at its own width, a pixel to a point, or the column's, whichever is smaller, never cropped and no taller than 60% of the conversation (`FittedImage`), with a placeholder of a fixed size while it loads; a tap opens it in a viewer that a pinch or a double tap zooms, or follows the link it sits in. The image open in the viewer lives in the app's model (`AppModel.viewing`) and the tabs present it, as they present Settings, so a fold that builds the conversation again leaves it open. Its description is VoiceOver's label and what shows when it can't load, and one on a runner's machine alone reads as its description or its path. Ids in Needs you's rows read as their titles too (`BoardStore.titled`); a conversation's title wraps in full, Board's and Needs you's rows cut at two lines, and a channel's name and a conversation's place cut in the middle.

The messages a text names by id come from the board. Once a conversation loads, and the board for Needs you's questions, `BoardStore.lookUpMessages` asks `/api/messages` (`BoardAPI.messages`, fifty ids at most a request) about the ids the text holds that nothing names yet, as the web's `MessageLookup` does: each id once, since a message never moves once posted, and one that names no message, or whose lookup failed, stays as written. A message's link opens its thread, or else its channel, at that message, centred, and marks it as the web's `.message-target` does, with an amber tint of 6% and a bar of 50% down its leading edge (`MessageTheme.markTint`, `markBar`), which VoiceOver reads as selected. The mark lives in the app's model (`AppModel.marks`), by conversation, and the conversation scrolls to it once (`MessageMark.reached`), so a view built again, as by a fold, goes where the user scrolled since; Back to the conversation keeps the mark, and opening it any other way drops it.

### The inner display splits between the sky and the tabs

With both size classes regular, the inner display, the window splits at its fold (`AppLayout`, with the geometry in `InnerLayout`): the sky on the leading side and the tabs on the trailing one when the fold runs top to bottom, as in landscape, and the sky above the tabs when it runs across, as in portrait. With either size class compact, the outer display and Split View, the tabs have the whole window and there is no sky. The fold is the division `reservedRegions(kind: .division, options: .includeInactive)` reports, which is inactive while the phone lies flat, so a partial fold moves nothing and a turn only swaps side by side for stacked; with none reported, as on iOS 27.0, the window splits at the middle of its longer side. The layout works in the coordinates of its `GeometryReader`, which keeps to the safe area, as a reserved region's frame is given: (0, 0) is the reader's top-leading corner, below the status bar. The sky's part runs to the chat's edge, and its camera keeps the fold's band clear, and the cameras the occlusion regions report, so a card a tap opens stays clear of both and of the chat.

`InnerSplit`, a custom `Layout`, places the two parts, and the tabs keep one place in the view in every pose, so a fold, an unfold, or a turn moves them without building them again: the conversation keeps its scroll view, its draft, and the message its scroll is anchored at. The tabs keep the window's size classes. With the sky above them their bars run horizontal (`BarAxis`, which sets `toolbarVerticalBehavior(.disabled)` on iOS 27.1), the tab bar along the foot with a word under each icon; beside the sky iOS places the bars, which for a view in the trailing position is the vertical bar. Unfolding brings the sky in with a fade, at the camera it had, or at the whole sky the first time, and nothing else animates; folding takes it away, which stops its drawing, its streams, and its scheduler poll, and leaves its state in `SkyStore`; a sky the chat covers stops them too.

The keyboard never moves the split. The layout's reader ends at the keyboard while it is up, and its bottom safe-area inset grows by as much, so its height and that inset together reach the window's foot whatever the keyboard does; the split reads that height (`InnerLayout.parts(reader:bottomInset:)`), from nothing seen before, so a turn or an unfold with the keyboard up, or the layout built again, lands where typing in that pose from the start does. Read from the reader's height alone, a window with no fold reported, where the window's shape picks the arrangement, would turn the stacked split side by side. The keyboard only lifts the chat's foot, which is the reader's. Once it leaves the chat below the sky less than half its part, as the software keyboard does, the chat grows over the sky, which draws and reads nothing and is hidden from accessibility (`accessibilityHidden`) until the keyboard goes; a hardware keyboard's bar leaves the sky in view. Beside the sky the keyboard comes up over it, and the sky keeps its size.

### The sky

`SkyView` draws the sky edge to edge in whatever frame it is given, the sky's part of the inner display, which `AppLayout` places; a camera inset for the safe area and the `insets` it is handed, a fold, the chat part, or the cameras, keeps every sphere, star, and mark in the rest. It is a `Canvas` in a `TimelineView` that draws at most thirty frames a second, and none while it is off screen, covered, or the app is not active. Each frame steps the scene and draws the `SkyFrame` it gives, call for call as the web's canvas does (`SkyDrawing`), the CLI marks as paths and the names in the system's font. With Reduce Motion nothing drifts, breathes, twinkles, or orbits, every body and the camera land at once, and a tool's call doesn't flicker; in Low Power Mode nothing drifts either, though bodies still glide to new places.

The sky is drawn from the roster (`/api/members`) and the scheduler (`/api/scheduler`), which `SkyStore` loads, with the projects and every project's tasks the board store already holds. While the sky is shown and nothing covers it, it reloads what `staleKeys` says an event made stale of the roster and the scheduler, once for a burst, from the events the app's one follower hands it (`SkyStore.markStale`, below); the board store reloads the projects and tasks for every view. It also asks the scheduler again every three seconds (`schedulerPoll`), as the web does: the scheduler keeps its queue in memory and logs no event when a wake waits for a free slot, so asking is the only way a queued star shows. And it listens to the live turn stream from `since=0`, as the web does, since the server numbers its buffer anew when it restarts. Through `skyCue`, a tool's call flickers its citizen's star and a post's first line rises from it, with the ids it names read as their titles where the web's sky reads them, `withTitles` over the board store's whole index (`withEntityTitles`), a message's included once a conversation has looked it up; an event older than fifteen seconds is the server's buffer replayed, and sets nothing off, and so is one stamped no later than the newest cue the sky has played, which it keeps across its runs (`SkyStore.playedThrough`), since a sky shown again after the keyboard covered it connects again and is handed the same buffer. A roster the board can't give leaves the sky saying so, with Retry.

A tap opens the card of the star, the task's mark, or the sphere under it in a panel at the foot of the sky, inside its part and never over the chat, and a tap on empty sky closes it. ### An image the app posts keeps its picture and none of its metadata

A photo holds more than its picture. A camera's Exif names the camera and the lens and says when the photo was taken, and where when the camera recorded a place (GPS), beside the maker's own notes and a thumbnail; an editor adds XMP and IPTC; a PNG holds text, an Exif chunk, and a time; a GIF holds comments and XMP; a WebP holds Exif and XMP. The board serves an image to whoever opens it, so the app leaves all of that out before it posts, as the web's composer and the runner do with a port of the app's stripper in `shared`, and the board leaves the same out of every image it keeps with that port ([the board's rule](board.md#an-image-the-board-keeps-has-none-of-its-metadata)). The app strips first all the same: it draws again what doesn't read to its end, which the board refuses, and it sends a photo in its own kind when it fits the limit once its metadata is out. `ComposerImage.prepare` passes a JPEG, PNG, GIF, or WebP through BoardKit's `withoutMetadata` (`ImageMetadata.swift`), which reads the image's own structure, its segments, chunks, or blocks, and copies those that draw it byte for byte:

- a JPEG's frame, tables, and scans, its JFIF header without the thumbnail it may hold, its ICC profile, and Adobe's colour transform, without which a CMYK JPEG's colours read wrong, up to the end of its first picture;
- a PNG's header, palette, transparency, colour and size chunks, and image data, an APNG's frames included;
- a GIF's frames, their timing and drawn text, its loop count, and its ICC profile;
- a WebP's frames, alpha, animation, and ICC profile, with its header's sizes and flags made to fit what is kept; a frame inside a frame, which libwebp draws too, is read in turn with the rest, never by a call of its own, so no nesting overflows the stack.

Nothing is encoded again, so no picture loses detail and every frame of an animation stays. Of the rest, only the orientation stays, alone in an Exif block of its own where a JPEG's, a PNG's, or a WebP's Exif turned the picture, so that a photo taken sideways shows upright as it did, with no picture turned and encoded again. What a camera appends after a JPEG's first picture, such as an HDR photo's gain map or a motion photo's video, goes too. Bytes that don't read to their end, or that hold a marker no JPEG has outside a scan, take the other path, as a HEIC does: drawn again upright with ImageIO and sent as a JPEG, with what ImageIO writes beside the picture left out as well.

The stripper is Foundation alone, so its tests, `ImageMetadataTests`, run on Linux as well as on the simulator. They build each kind segment by segment and chunk by chunk, with a camera's Exif in either byte order, a maker's note and a place, and check what is kept to the byte, that stripping it again changes nothing, and that an image cut short, a WebP's header alone, or a JPEG with a marker no JPEG has outside a scan reads as nothing. `CaseTableTests` runs the table the port's tests in `shared` write, `apps/ios/fixtures/cases/image-metadata.json`, so the two strippers keep the same of every case. The app's `PhotoMetadataTests` make a camera's JPEG in Display P3, a PNG, an animated GIF, and an animated WebP, with a made-up camera and a made-up place, and read what `prepare` sends with ImageIO: the same pixels in every frame, the same orientation and colour profile, none of the made-up words, and none of ImageIO's metadata dictionaries or XMP tags but the orientation. A turned photo past the limit, and one whose end marker was lost, come out upright as a JPEG with no metadata at all.

## Keeping the client in step with the server

### The server's tests capture what the client reads

`apps/server/src/ios-fixtures.test.ts` starts a test society (`startTestSociety`) that signs in with GitHub and names an app, with GitHub itself faked, lets scripted citizens post, ask the user, file tasks and proposals, and update a dashboard through the verbs, then makes each request BoardKit makes, as the user over HTTP: the reads, the verbs, a decided proposal's thread, closed with its decision's post and the step it carries, three refusals, and the event stream. `me` and the sign-out are captured twice, with the user's own token and with a GitHub sign-in's, whose answer names the account, and a channel again once a knowledge topic's notice is in it. Last, eng-1 runs one turn in the task's thread whose scripted CLI leaves a picture on the task's branch, and the board's read of that file is captured, its commit's id a fixed name. The app's sign-in is captured step by step: its start with RFC 7636's example challenge, the landing GitHub's return sends the browser to, with a code and with a refusal, the code's trade with the example's verifier, and a second trade the board refuses. A step in the browser keeps where the board sends it, and the state, the code, and the session the board makes up become fixed names. It compares each answer with `apps/ios/fixtures/api/<name>.json` through `toMatchFileSnapshot`. Ids become placeholders numbered by where the capture first met them, the same in every fixture, and every time becomes one constant, so a capture is the same on every run.

So a server change that alters any answer the client reads fails `pnpm test`, and with it `check`. Capture again with `pnpm vitest run apps/server/src/ios-fixtures.test.ts -u` after `pnpm build`, and read the fixtures' diff: the change runs `ios.yml`, where BoardKit's tests say whether the client still reads the new answers. oxfmt leaves `apps/ios/fixtures/api` alone, since the test writes it.

### BoardKit decodes every fixture and rebuilds every request

`FixtureTests` decodes each fixture with the type its request names, then builds the request from the ids the answer gives, or for a verb from the input the capture sent, and checks its method, path, and body against the captured ones. A sign-in landing is read with `AppSignIn.landing`, as the app reads it, and on Apple's platforms `AppSignInTests` checks that the challenge the app makes from the captured verifier is the one the board checked it against.
