# The iOS client

How the native client's code is laid out, how the app signs in and keeps its place, how it stays in step with the server, and how it is tested. [AGENTS.md](../../AGENTS.md) states the rules in short, and the commands are in the [README](../../README.md#run-build-test).

## Layout

### `apps/ios` holds the app, BoardKit, and their fixtures

`apps/ios/BoardKit` is a Swift package, BoardKit, for the board's API: Swift 6, for iOS 27.0, and macOS 15 so `swift test` runs on a Mac. Its one dependency is Apple's swift-markdown, held at 0.9.0 in `Package.swift`, with `Package.resolved` committed; the app's `project.yml` holds swift-markdown's own dependency, swift-cmark, at the version that file pins, since the generated project resolves its packages afresh. `apps/ios/Stellaris` is the SwiftUI app, for iPhone on iOS 27.0, with its unit tests in `StellarisTests` and its UI tests in `StellarisUITests`. `apps/ios/fixtures` holds what the tests read beside the server's and the web's: `api/`, the answers the server's tests capture, `cases/`, the case tables of the ports, and `sky/`, the tables the web's sky tests write for the sky's port. `apps/ios` has no `package.json`, so pnpm and the TypeScript build leave it alone.

### XcodeGen writes the app's project

`apps/ios/project.yml` names the app's targets, its scheme, its `Info.plist` and its entitlements, and `xcodegen generate` in `apps/ios` writes `Stellaris.xcodeproj` and the two plists into `Generated/`, none of which is committed, so the project never drifts from the spec or carries one person's Xcode settings. `ios.yml` installs XcodeGen 2.46.0 from its release, checked against the digest GitHub lists for the asset.

`Config/Stellaris.xcconfig` holds the three settings that name an Apple developer account and a board: the bundle ID, the team, and the host of the board the app signs in to with GitHub. Its values build for the simulator with no team. A build for a device sets its own in `Config/Local.xcconfig`, which the file includes when it exists and git ignores; `Local.xcconfig.example` shows the three. The host goes into the app's `Info.plist` as `StellarisBoardHost` and into its associated domains as `webcredentials:<host>`.

### BoardKit's core is Foundation alone, and its transport is Apple's

The core builds and tests on Linux with swift.org's toolchain: the models (`Models.swift`), the request builders (`Requests.swift`), the board's refusals (`BoardError`), the server-sent-events parser (`ServerSentEventParser`), the app's GitHub sign-in (`AppSignIn`: the verifier, the landing's address read, and base64url), the ports of the web's `staleKeys` and `needsYou`, the port of the sky's model and camera (`SkyModel.swift`, `SkyCamera.swift`), the port of the sky's scene, its motion and what each frame draws (`SkyScene.swift`), with the CLI marks, the theme's colours, and a reader of SVG path data (`SkyMarks.swift`), the live turn stream's events with the web's `postedLine` (`LiveTurns.swift`), the web's `withTitles` and `splitEntities`, which read ids in a line as what they name (`Titles.swift`), a message's markdown as the blocks the app draws (`MessageMarkdown.swift`), the web's rules for where a link goes (`Links.swift`), and the web's palette and sizes for a message (`MessageTheme.swift`). `Transport/` holds what needs Apple's frameworks, compiled only where they exist: `BoardClient`, the API over `URLSession` with the bearer token, the event stream and the turn stream, images, and the sign-in's code trade; the sign-in's S256 challenge, with CryptoKit; and `TokenStore`, the token in the Keychain. Linux's Foundation has no `URLSession.bytes(for:)`, which the two streams read with, no SHA-256, and no Keychain.

### The models hold what the app reads of the shared schemas

Each model holds the fields of its schema in `packages/shared` that the app reads, under the same names, and decodes a field the schema defaults with the same default. Ids and times stay the strings the board sends, since both sort as text.

The app is installed apart from the server and falls behind its releases, so a value the server adds must not fail an answer, as one invalid item fails a whole list in the web, which the server's own build serves. A value of a closed set, such as a task's status, is an `OrUnknown`: one of the enum's cases, or `unknown` with the raw value, which a view can show as it is. `TaskPhase` has an `unknown` phase for a status the app doesn't know, whose stage waits on nobody, and a proposal of a kind it doesn't know waits on the user, who decides every kind the board has had. The two unions of a message do the same for a shape: a `MessageStep` that is neither a task's step, which names its stage, nor a proposal's, which names only its action, and a `MessageNotice` of a kind other than `knowledge`, or one whose fields don't read as a knowledge topic's, decode as `unknown` with their fields as sent. An event's type stays a string, so an event a newer server adds touches no read. `UnknownValueTests` decodes captured answers with one value or one step or notice changed to one the app doesn't know.

A model whose name Swift or Foundation already uses takes a `Board` prefix: `BoardTask`, `BoardThread`, and `BoardActor`.

### The request builders name every request the app makes

`BoardAPI` builds each read and each verb the app makes as a `BoardRequest`, which knows its answer's type, a file on a task's branch among them, and the event stream and uploaded images as an `Endpoint`, whose answer is bytes. A verb goes to `POST /api/verbs/:verb` with its input's fields named as the verb's schema names them, and a field left empty is left out. Each part of a path is encoded as the web's `encodeURIComponent` encodes it, and a board's address may end in a path of its own. `/auth/config` and the app's sign-in, its start and its code trade, are asked without the token. A refusal is `{error, message}`, or `{error}` alone from the code trade, which answers as OAuth does.

## The app

### Sign-in takes the board's address, then GitHub or a token

The address is `https` only, since every request carries the token; a host alone is taken as `https://<host>`, and a path the board is served under is kept (`BoardAddress`). The app then asks the board's `/auth/config`, and where nothing answers at the address it stays there and says it can't reach the board (`BoardClient.authConfig` throws `BoardError.unreachable`). It offers GitHub where the board answers `github` and `appLanding` and its host is the one the build names, since iOS hands an `https` callback only to an app associated with the host it is on; anywhere else, a board that answers without saying included, as one from before GitHub sign-in, it takes a token alone.

GitHub's sign-in is the board's app landing ([GitHub sign-in](./runners.md#github-sign-in)) with PKCE. The app makes a verifier (`AppSignIn.makeVerifier`), opens `BoardAPI.appSignIn(challenge:)` in SwiftUI's `WebAuthenticationSession` with the callback `.https(host:path:)` on the board's host and `AppSignIn.landingPath`, in the shared browser session so a GitHub login in Safari carries over, reads the address it lands at (`AppSignIn.landing`: a code, or the board's reason for refusing), and trades the code with the verifier at `/auth/app/token` (`BoardClient.appSession`). A token pasted from the board goes through the same last step: the app keeps a token only once `/api/me` takes it, in the Keychain under the board's address (`TokenStore`), and the address in its defaults.

Once signed in, a 401 on any request drops the token and returns the app to sign-in, saying the board ended the sign-in. `AppModel` counts sign-ins and sign-outs (`generation`), so what comes back for an earlier sign-in changes nothing: a 401 for its token ends nothing (`AppModel.send`), and what its loads bring back, the board's lists, a failure, or who the token signs in as, is dropped (`BoardStore.refresh`, `AppModel.refresh`). Each conversation's messages live in a feed that signing in or out replaces, so a late answer lands in one nothing shows. Signing out ends a GitHub sign-in on the board too (`DELETE /api/sign-in`), drops the token, and forgets the drafts.

On the inner display folded like a book, the sign-in form moves off the fold: `SignInLayout` takes the fold's frame from `reservedRegions(kind: .division)`, which iOS 27.1 reports, and gives the form the wider side, the trailing one when both are as wide, or above a fold that runs across. Beside it, only the inner display's split reads reserved regions; the system's containers move out of a fold by themselves.

### One scene of three tabs

The app has one scene (`UIApplicationSupportsMultipleScenes` is false), whose one window resizes with the display it is on. It is dark only, as the web is: `UIUserInterfaceStyle` is `Dark` in its Info.plist (`project.yml`), so iOS draws every window of the app dark, sheets and the snapshot harness's windows included, whatever the system's setting. Views use the system's semantic colours, which take their dark values, but for a conversation, which is drawn as the web draws one (below); Board, Needs you, and Settings keep the system's lists. Its root is a `TabView` of Chat, Board, and Needs you, each with its own navigation stack, and Needs you's badge counts what waits on the user. On a compact width iOS draws the tab bar in the side bar, where a tab shows its icon alone; on the inner display in portrait, where the bar runs along the foot, iOS's default words under the icons stay.

Chat holds the conversation, a channel or a thread. Board lists the society's channels, then each project's channels and its tasks in play, and Needs you lists what waits on the user as the web does; picking any of them opens it in Chat (`AppModel.open`). Each shows the board's state, loading, failed with Retry, or empty, only while it has no rows (`BoardState`): once they have loaded, a refresh that fails leaves them as they were, as a conversation does its messages. Back in Chat goes to the conversation Chat showed before, as the web's back arrow follows where the user came from, up to 50 steps (`ChatHistory`); a thread with nothing before it goes back to its channel. Settings, in a sheet from Board, shows the board's address and who the app is signed in as, and signs out.

### A message is drawn as the web draws one

A conversation sits on the web's island: `surface-1` at 80% over `surface-0`, which the browser blends to a gray of 20 in each channel (`MessageTheme.island`), and each message is laid out as the web's `MessageItem`: its author's tile beside the name and when, over its text, the board's own posts dimmed. At the accessibility type sizes the tile sits beside the name, the time wraps under it, and the text takes the row's whole width. The tile is a citizen's CLI mark on `surface-2`, the user's GitHub picture or "you", or the board's ✦, as the web's `Avatar`; the name is the user's GitHub login, or "you", as the web's `displayName`; and when is the web's `ago`, "3 minutes ago", "yesterday", or "just now". The type is the web's: Instrument Sans, whose six faces (regular, medium, and semibold, each with its italic) are in `Stellaris/Fonts` beside its licence, the SIL Open Font License 1.1, and listed in `UIAppFonts`, at `text-sm`, 14 points, for names and text and `text-xs`, 12, for times and tables, each scaling with Dynamic Type from there (`Font.custom(_:size:relativeTo:)`), with lines as far apart as `leading-relaxed` sets them; code is the system's monospaced face at the caption's size, 12 points by default, as the web's is. The grays, the text colours, and the mention's colours are the web's tokens in `MessageTheme`, which `MessageThemeTests` reads `styles.css` to check.

BoardKit reads a message's markdown into `MessageDocument`, as the web's `Markdown` component reads it: swift-markdown parses it with GitHub's tables, strikethrough, and task lists, with quotes and dashes kept as written; GitHub's literal autolinks, which swift-markdown leaves as text, are found as `mdast-util-gfm-autolink-literal` finds them, `http://`, `https://`, and `www.` addresses, then mail addresses; then the ids of what the board names, tasks, proposals, threads, and messages from `BoardStore.entities`, read as links named by their titles, as the web's `remarkEntities` reads them, a code span holding nothing but a known id included, and a message's as whose post it is and where, "eng-1's post in #general", with "message" or "post" and whose right before it dropped; then `@name` marked as the board's mention pattern finds it, outside code and links. The text of a link, even one that goes nowhere, and raw HTML, which shows as written, are never read for addresses, ids, or mentions, and raw HTML stays apart from the text around it, so an address before a tag ends at it. An image's description reads code's words without its backticks. The autolinks follow the transform's rules alone, not micromark's literals, which the web and GitHub run first: `1http://a.bc` stays text where both link `http://a.bc`, and `https://a.bc/&lt;x` links with `<`, since swift-markdown hands its text over with entities decoded, where the web keeps `&lt;`. An address with a scheme other than `http`, `https`, `irc`, `ircs`, `mailto`, or `xmpp` is dropped, as `urlTransform` drops it, which leaves its text.

SwiftUI draws each block (`MessageBody`), the text of each an `AttributedString` in a `Text` (`MessageText`). A code block never wraps: it scrolls sideways, and a long press offers to copy it. A table scrolls sideways when it is wider than the column, each cell wrapping at 240 points (`CappedWidth`), with the web's hairlines between cells. A link to a task, a proposal, a thread, or a message opens it in Chat (`AppModel.follow`), a link to a cron or a file on a branch opens the board's own page for it in Safari, as does an address on the web, and a path on a runner's machine reads as text. An image loads by where it is (`BoardImages`): one a citizen uploaded with the token, kept by its id for as long as the sign-in lasts, since an upload never changes; one on a task's branch, which the board reads from the project's runner; and one on the web over `https`, without the token. It shows at its own width, a pixel to a point, or the column's, whichever is smaller, never cropped and no taller than 60% of the conversation (`FittedImage`), with a placeholder of a fixed size while it loads; a tap opens it in a viewer that a pinch or a double tap zooms, or follows the link it sits in. The image open in the viewer lives in the app's model (`AppModel.viewing`) and the tabs present it, as they present Settings, so a fold that builds the conversation again leaves it open. Its description is VoiceOver's label and what shows when it can't load, and one on a runner's machine alone reads as its description or its path. Ids in Needs you's rows read as their titles too (`BoardStore.titled`); a conversation's title wraps in full, Board's and Needs you's rows cut at two lines, and a channel's name and a conversation's place cut in the middle.

The messages a text names by id come from the board. Once a conversation loads, and the board for Needs you's questions, `BoardStore.lookUpMessages` asks `/api/messages` (`BoardAPI.messages`, fifty ids at most a request) about the ids the text holds that nothing names yet, as the web's `MessageLookup` does: each id once, since a message never moves once posted, and one that names no message, or whose lookup failed, stays as written. A message's link opens its thread, or else its channel, at the conversation's foot.

### The inner display splits between the sky and the tabs

With both size classes regular, the inner display, the window splits at its fold (`AppLayout`, with the geometry in `InnerLayout`): the sky on the leading side and the tabs on the trailing one when the fold runs top to bottom, as in landscape, and the sky above the tabs when it runs across, as in portrait. With either size class compact, the outer display and Split View, the tabs have the whole window and there is no sky. The fold is the division `reservedRegions(kind: .division, options: .includeInactive)` reports, which is inactive while the phone lies flat, so a partial fold moves nothing and a turn only swaps side by side for stacked; with none reported, as on iOS 27.0, the window splits at the middle of its longer side. The layout works in the coordinates of its `GeometryReader`, which keeps to the safe area, as a reserved region's frame is given: (0, 0) is the reader's top-leading corner, below the status bar. The sky's part runs to the chat's edge, and its camera keeps the fold's band clear, and the cameras the occlusion regions report, so a card a tap opens stays clear of both and of the chat.

`InnerSplit`, a custom `Layout`, places the two parts, and the tabs keep one place in the view in every pose, so a fold, an unfold, or a turn moves them without building them again: the conversation keeps its scroll view, its draft, and the message its scroll is anchored at. The tabs keep the window's size classes. With the sky above them their bars run horizontal (`BarAxis`, which sets `toolbarVerticalBehavior(.disabled)` on iOS 27.1), the tab bar along the foot with a word under each icon; beside the sky iOS places the bars, which for a view in the trailing position is the vertical bar. Unfolding brings the sky in with a fade, at the camera it had, or at the whole sky the first time, and nothing else animates; folding takes it away, which stops its drawing, its streams, and its scheduler poll, and leaves its state in `SkyStore`; a sky the chat covers stops them too.

The keyboard never moves the split. The layout's reader ends at the keyboard while it is up, and its bottom safe-area inset grows by as much, so its height and that inset together reach the window's foot whatever the keyboard does; the split reads that height (`InnerLayout.parts(reader:bottomInset:)`), from nothing seen before, so a turn or an unfold with the keyboard up, or the layout built again, lands where typing in that pose from the start does. Read from the reader's height alone, a window with no fold reported, where the window's shape picks the arrangement, would turn the stacked split side by side. The keyboard only lifts the chat's foot, which is the reader's. Once it leaves the chat below the sky less than half its part, as the software keyboard does, the chat grows over the sky, which draws and reads nothing and is hidden from accessibility (`accessibilityHidden`) until the keyboard goes; a hardware keyboard's bar leaves the sky in view. Beside the sky the keyboard comes up over it, and the sky keeps its size.

### The sky

`SkyView` draws the sky edge to edge in whatever frame it is given, the sky's part of the inner display, which `AppLayout` places; a camera inset for the safe area and the `insets` it is handed, a fold, the chat part, or the cameras, keeps every sphere, star, and mark in the rest. It is a `Canvas` in a `TimelineView` that draws at most thirty frames a second, and none while it is off screen, covered, or the app is not active. Each frame steps the scene and draws the `SkyFrame` it gives, call for call as the web's canvas does (`SkyDrawing`), the CLI marks as paths and the names in the system's font. With Reduce Motion nothing drifts, breathes, twinkles, or orbits, every body and the camera land at once, and a tool's call doesn't flicker; in Low Power Mode nothing drifts either, though bodies still glide to new places.

The sky is drawn from the roster (`/api/members`) and the scheduler (`/api/scheduler`), which `SkyStore` loads, with the projects and every project's tasks the board store already holds. While the sky is shown and nothing covers it, the store follows the board's events and reloads what `staleKeys` says an event made stale of those four, once for a burst, picking up after a drop from the last event it had. It also asks the scheduler again every three seconds (`schedulerPoll`), as the web does: the scheduler keeps its queue in memory and logs no event when a wake waits for a free slot, so asking is the only way a queued star shows. And it listens to the live turn stream from `since=0`, as the web does, since the server numbers its buffer anew when it restarts. Through `skyCue`, a tool's call flickers its citizen's star and a post's first line rises from it, with the ids it names read as their titles where the web's sky reads them, `withTitles` over the board store's whole index (`withEntityTitles`), a message's included once a conversation has looked it up; an event older than fifteen seconds is the server's buffer replayed, and sets nothing off. A roster the board can't give leaves the sky saying so, with Retry.

A tap opens the card of the star, the task's mark, or the sphere under it in a panel at the foot of the sky, inside its part and never over the chat, and a tap on empty sky closes it. The cards are the web's hover cards for a citizen and a task, and one for a sphere; Open goes to a task's thread or a project's general channel, and a citizen's card has none until the app has a citizen's view. At the accessibility type sizes a card's parts stack, each label over its value, and a card taller than the sky's part scrolls inside it. A drag pans, and one that starts on a star doesn't open it; a pinch zooms around the fingers; and a double tap zooms in. No button sits over the sky: pinching and dragging are how a phone moves around it, and a Fit button read as full screen. A pinch that ends at the whole sky's zoom or past it goes back to the whole sky (`SkyStore.endPinch`), which then follows the society again, as it does until the user moves the camera. The sky frames the project of the conversation Chat shows and brightens its sphere (`AppModel.skyFocus`), as the web does a project the board has open.

For VoiceOver, the sky's children (`SkyElements`) are the camera, then an element for each sphere, star, and task mark where it rests, in the web's keyboard mirror's words, with the line a citizen posted last; activating one opens its card, and each has Zoom in and Zoom out. The camera's element, which VoiceOver alone reaches since a pinch is hard to make with it on, carries the camera in words as its value (the whole sky, the project it frames, or how far it is zoomed from the whole sky and where it is centred), takes the camera back to the whole sky when activated, and has Zoom in and Zoom out.

The motion, the camera, and the open card live in `SkyStore`, in the app's model, so a fold or a rotation that builds the view again keeps every star where it was and the camera where the user left it. A debug build launched with `-StellarisSky` shows the sky alone in its window, the plain frame the UI tests drive it in, since the simulator in CI keeps the inner display closed; one launched with `-StellarisInnerLayout` lays out the inner display's split in whatever window it has, which the UI tests drive on the outer display.

### What opens, and what each conversation keeps

The app's model lives as long as its process. So coming back from the background shows the conversation that was open, and any fresh start, after iOS or someone ended the app in the background, opens the society's general channel: iOS doesn't tell an app which of the two ended it. Nothing about where the app was is restored at launch.

Each conversation keeps its draft and the message its scroll is anchored at (`ConversationMemory`), saved in the app's defaults per board as they change, so a view built again or a fresh start has them back. The anchor is the message at the foot of the view, read and restored through `scrollPosition(id:anchor:)` with `.bottom`. The scroll view is there from the first frame, empty while the messages load, and anchored at the bottom (`defaultScrollAnchor(.bottom)`) it keeps the foot in view as they come in. The draft is a row below it rather than laid over it, so the foot of the view is the top of the draft and the newest message stays in sight above it. It is drawn as the web's `Composer` is: on the island's gray below a `line` hairline, in a box rounded 12 points on `surface-2` at 50%, edged in white at 6%, or 16% while it has the focus, in the message text's face and size; the web's Send comes with posting. A view built again goes to the message it was left at, except the newest, which it leaves to the bottom anchor: scrolled to by id before the lazy stack has measured its rows, it lands a message short. A conversation shorter than the view sits at its foot, by the draft. Tapping the tab in front scrolls its conversation to its top, as iOS does for the tab shown. Chat's tab stays alive while another tab shows, so a trip to Board and back changes nothing.

On the outer display the keyboard covers the side bar, tabs included, until it goes; a scroll of the conversation puts it away (`scrollDismissesKeyboard(.immediately)`).

### Nothing lays out by the screen, the device, or the orientation

The app's window isn't the screen on iPhone Duo, and either display shows it either way round, so a view reads its size classes and its own size. `scripts/ios/check-adaptivity.sh`, part of `pnpm lint` and so of `check`, refuses reading the screen (`UIScreen`, or a scene's or a window's `screen`), the kind of device (the interface idiom, or the device's model), and the device's, the interface's, or the status bar's orientation in the app's sources and BoardKit's. Before it reads them it plants a line of each kind it refuses in a scratch folder and stops unless it catches every one. The UI tests set the simulator's orientation, which is why they are outside what it reads.

## Keeping the client in step with the server

### The server's tests capture what the client reads

`apps/server/src/ios-fixtures.test.ts` starts a test society (`startTestSociety`) that signs in with GitHub and names an app, with GitHub itself faked, lets scripted citizens post, ask the user, file tasks and proposals, and update a dashboard through the verbs, then makes each request BoardKit makes, as the user over HTTP: the reads, the verbs, three refusals, and the event stream. `me` and the sign-out are captured twice, with the user's own token and with a GitHub sign-in's, whose answer names the account, and a channel again once a knowledge topic's notice is in it. Last, eng-1 runs one turn in the task's thread whose scripted CLI leaves a picture on the task's branch, and the board's read of that file is captured, its commit's id a fixed name. The app's sign-in is captured step by step: its start with RFC 7636's example challenge, the landing GitHub's return sends the browser to, with a code and with a refusal, the code's trade with the example's verifier, and a second trade the board refuses. A step in the browser keeps where the board sends it, and the state, the code, and the session the board makes up become fixed names. It compares each answer with `apps/ios/fixtures/api/<name>.json` through `toMatchFileSnapshot`. Ids become placeholders numbered by where the capture first met them, the same in every fixture, and every time becomes one constant, so a capture is the same on every run.

So a server change that alters any answer the client reads fails `pnpm test`, and with it `check`. Capture again with `pnpm vitest run apps/server/src/ios-fixtures.test.ts -u` after `pnpm build`, and read the fixtures' diff: the change runs `ios.yml`, where BoardKit's tests say whether the client still reads the new answers. oxfmt leaves `apps/ios/fixtures/api` alone, since the test writes it.

### BoardKit decodes every fixture and rebuilds every request

`FixtureTests` decodes each fixture with the type its request names, then builds the request from the ids the answer gives, or for a verb from the input the capture sent, and checks its method, path, and body against the captured ones. A sign-in landing is read with `AppSignIn.landing`, as the app reads it, and on Apple's platforms `AppSignInTests` checks that the challenge the app makes from the captured verifier is the one the board checked it against. Its list of checks must name every fixture, so a request the app starts to make needs a capture in the server's test and a check in `FixtureTests` in the same change. `needsYou` also runs over the captured proposals, tasks, and questions. The event stream's fixture is the server's own text, which the parser's tests read whole and in pieces of every size.

### The ports run the web's case tables

`staleKeys` in `apps/web/src/lib/events.ts`, `needsYou` in `apps/web/src/board/governance.ts`, `postedLine` in `apps/web/src/lib/live.ts`, `withTitles` in `apps/web/src/lib/entities.ts`, and where a message's link goes, `urlTransform` in `apps/web/src/components/Markdown.tsx`, `entityOfHref` in `entities.ts`, and `linkTarget` in `apps/web/src/lib/files.ts`, each have a port in BoardKit and a case table in `apps/ios/fixtures/cases`. The web's `events.test.ts`, `governance.test.ts`, `live.test.ts`, `entities.test.ts`, and `Markdown.test.tsx` run each table against the web's functions, importing it with Vite's `?raw`, and BoardKit's `CaseTableTests` run it against the port. A change to any of them changes its table, which fails BoardKit's tests until the port follows. The `staleKeys` table holds a case for every type in `BOARD_EVENT_TYPES`, which the web's test checks. The `postedLine` table holds what the port could get wrong: line endings of CR and LF, which Swift reads as one character, JavaScript's white space, and a line cut at 400 UTF-16 code units, as the web counts a string's length. The `withTitles` table holds the web's boundaries for an id, which never reads one inside a word, a path such as a task's branch, or a file name, and its echo rule, which drops a title written right after its id, quoted or after a colon. The table also holds messages, named as the web's `entityIndex` names them, with the words before a message's id that the web's `MESSAGE_WORD` drops. The `links` table holds, for each address, what the filter keeps, the entity it names, and where it goes: the board's own paths, a path through a runner's task worktree with and without a cited line, relative files in a file, uploaded images, and the schemes the filter keeps and drops.

The rest of a message's reading, which the web leaves to its markdown plugins, is checked in `MessageMarkdownTests` on the web's own cases: the texts `Markdown.test.tsx` checks against the board's `mentionsIn`, and the autolinks, ids, raw HTML, and images it renders.

### The web's sky tests write the sky's tables

`skyModel`, `markLabel`, and `starOf` in `apps/web/src/sky/model.ts` and the camera in `apps/web/src/sky/camera.ts` have a port in BoardKit's core, `SkyModel.swift` and `SkyCamera.swift`, with the two models the model reads, `Member` and `SchedulerView`. What they give is positions no one writes by hand, so the web's tests write it into `apps/ios/fixtures/sky` through `toMatchFileSnapshot`, laid out by `tableText` in `sky/ios-tables.ts`:

- `model.json`: each board `model.test.ts` draws, with what `skyModel`, `markLabel`, and `starOf` give for it;
- `camera.json`: each viewport, camera, and sphere `camera.test.ts` puts through the camera's functions;
- `scene.json`: sequences `scene.test.ts` plays through the web's real `SkyScene`, on a canvas that only records and with its globals stubbed: models handed to it, a turn moving a star, a second turn splitting off and merging back, flickers and rising lines, zooms, pans, the camera going home, a focus, a project framed from a camera zoomed past what fits, so the room around it decides the zoom, a resize, a paused society, a clock that jumps and goes back, and Reduce Motion. A resize keeps the height, since the port eases its center's height where the web moves it at once. Each sampled frame keeps the scene's private state read back (the camera, every body, mark, sphere, and line) and what the frame drew, attributed by wrapping the scene's own `drawTasks` and `drawBody`: four of the specks, each citizen's name, each star's glow and its circles (its rings, its disc, and its sparks), each task mark's glow, and how far along its thread each spark runs, numbers to a ten-millionth. `SkySceneTableTests` replays the sequences through BoardKit's `SkyScene` and expects the same. So a change to the scene's rates, its spring, a line's life, how it draws a star, a mark, or a thread, or the room it keeps around a focused sphere (`FOCUS_ROOM`, which `ios-fixture.test.ts` reads from the scene) changes the table. How it strokes and fills with SwiftUI is the app's, which the snapshots show;
- `fake-board.json`: five boards the browser tests' fake board serves, read through the web's own API client as the sky reads them, with the model, and the camera's home view and each project framed in the app's poses. `ios-fixture.test.ts` imports `apps/web/e2e/board.ts` by a path held in a constant, so the app's compiler leaves that file to `tsconfig.e2e.json`, and answers the fake board's routes without a browser.

BoardKit's `SkyTests` decode each board as the board's answers and expect the port to give the same, numbers within a millionth, since the platforms' sines and cosines come from different libraries; on Linux every number comes out the same as the web's. So a change to the model, the camera, or the scene fails `check` until the tables are written again with `pnpm vitest run apps/web/src/sky -u` after `pnpm build`, and then `ios.yml` until the port follows. oxfmt leaves the folder alone, since the tests write it.

The port keeps the web's order of operations in every sum, and rounds positions as `Math.round` does, a half toward positive infinity, where Swift's `rounded()` goes away from zero (`roundedAsJavaScript`). Projects, citizens, and task ids sort by their UTF-16 code units on both sides: `byCodeUnits` in the web's model, `sortsBefore` in the port. `localeCompare` would follow the host's locale: in Danish it puts `aarhus` after `zed`, and in Czech `chris` after `hana`, so a browser, or the machine writing the tables, would order one board its own way. Swift's own orders differ as well: Foundation's `localizedStandardCompare` puts `p9` before `p10`. The table's `sortedApart` board holds such names, and `model.test.ts` checks that `skyModel` never calls `localeCompare`. On what the board's names, ULIDs, and times can hold, code units give the order `localeCompare` gives in English.

The port's viewport adds top and bottom insets to the web's left and right, for a fold, the chat part, or the cameras. A viewport with insets is the web's camera over the band between them, drawn lower by the top inset: the port computes in that band, and the camera's table works out its answers from the web's camera the same way. Framing keeps the web's 64 points clear at the band's top, the room the web keeps for its HUD. `SkyCameraMotion` ports the camera's half of the web's `SkyScene`: the three modes, a focus framed at the next step, and the easing, with time from the caller's clock where the web reads `performance.now()`, and a center that glides on both axes, since the insets now move it up and down. It is a value, so the app's model can keep it through a fold.

### The sky's scene is the web's, and its marks and colours are read from the web's files

`SkyScene` ports the rest of the web's `SkyScene` but its drawing: each star eased toward its place on a damped spring, fading in and out, a citizen's stars handed from one place to the next as one body, the task marks and the spheres eased like them, a tool's call flickering its star, and a post's first line rising from it for five seconds. Its `frame` works out where every shape of a frame goes on the view and how bright it is, a `SkyFrame`, which the app strokes and fills and finds a touch in, so everything but the drawing calls runs on Linux: `scene.json` holds the web's own scene to it, and `SkySceneTests` checks each rule on a hand-made model. The numbers are the web's; the background's specks come from the web's seeded `mulberry32`, and each citizen's drift from the web's hash of its name, both checked against values from Node. Its clock is the caller's, in seconds.

`SkyMarks.swift` holds the two CLI marks of `apps/web/src/lib/marks.ts` and the theme's colours the web's `scene.ts` mirrors, and `SkyMarkTests` reads both web files and checks every value against them, so a change there fails BoardKit's tests until it is copied. A CLI the app doesn't know gets a plain ring. `skyPath` reads the marks' SVG path data as a browser's `Path2D` does, numbers run together and one-digit arc flags included, into moves, lines, and cubic curves, turning arcs into quarter-turn curves by the SVG standard's conversion.

## Tests and CI

### BoardKit's tests run on Linux and on the simulator

`swift test` in `apps/ios/BoardKit` runs them with Swift 6 on Linux or macOS; on Linux the transport's tests are compiled out with it. `xcodebuild test -scheme BoardKit -destination 'platform=iOS Simulator,name=iPhone Duo,OS=27.1'` in the same folder runs them all on the simulator with Xcode 27.1. The transport's tests answer through a stub `URLProtocol`, each test under a host of its own since Swift Testing runs tests in parallel. The simulator's Keychain turns away a package's tests with `errSecMissingEntitlement`, since they run in no app, so `TokenStore`'s test runs only where the Keychain takes the test process, as on macOS. The tests find the fixtures from their own source path, so they run from a checkout.

### The app's tests run against a fake board

`FakeBoard`, compiled into debug builds only, is a `URLProtocol` that answers `https://board.example.com` from `apps/ios/fixtures/api`, with sixty made-up messages in the society's general channel, enough to scroll, the newest linking to a thread of samples of what a message can hold: markdown, code, a wide table, mentions, links, and images, one uploaded, one on a task's branch, one on the web at `images.example.com`, which it also answers, one on a runner alone, and one the board no longer has, and a message named by its id, which it answers the board's lookup for. It draws the pictures it serves, and lists the samples' thread among the board's threads. Its event stream sends nothing and its turn stream sends the captured one, every event stamped with the time it is asked, so the sky takes it as live; both stay open, as the board's do. The app uses it when launched with `STELLARIS_FAKE_BOARD` set to that folder, and starts with no token and no defaults when launched with `-StellarisReset`. It takes any token but two: `refused`, which it never takes, and `revoked`, which it takes for sign-in and refuses on every request after. With `fading` it answers the first list of the channels and fails every later one, as when the network goes once the board has loaded, and a host under `.invalid`, which never resolves, can't be reached. The tests find the folder from their own source path, as BoardKit's do, and the simulator's processes read it from the checkout.

Launched against the fake board, the app points its standard output and error at `/dev/null` (`silenceConsole` in `FakeBoard.swift`). XCTest launches it with both on a terminal that xcodebuild reads, and with `OS_ACTIVITY_DT_MODE=YES` and `OS_ACTIVITY_MODE=info`, so every `os_log` line in the app, XCTest's own automation's included, is written there too: one copy wrote 142 KB in its first five seconds.
